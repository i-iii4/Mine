# Аудит устойчивости хранилищ: структура, конфликты, потери

Related documents: [PRINCIPLES.md](PRINCIPLES.md) | [ARCHITECTURE.md](ARCHITECTURE.md) | [PLAN.md](PLAN.md) | [SPEC_STORAGE.md](SPEC_STORAGE.md) | [SPEC_IDENTITY_ROBUSTNESS.md](SPEC_IDENTITY_ROBUSTNESS.md) | [SPEC_OBSIDIAN_MARKDOWN_COMPAT.md](SPEC_OBSIDIAN_MARKDOWN_COMPAT.md) | [SPEC_COLLECTIONS_OBSIDIAN_LINKS.md](SPEC_COLLECTIONS_OBSIDIAN_LINKS.md) | [AUDIT_ACTIVATION.md](AUDIT_ACTIVATION.md)

Дата аудита: 12.08.2026. Метод: живые прогоны синтетических хранилищ через
`cold-space-audit` с инспекцией derived SQLite, плюс верификация каждого
поведения по коду. Помеченное «прогон» — воспроизведено; помеченное «код» —
прослежено до конкретных строк.

## Модель, из которой всё следует

Четыре правила идентичности определяют исход каждого сценария ниже:

1. **Карточка = относительный путь.** Слаг — путь `.md` от корня без
   расширения (`Cards/note`, не `note`). Скан рекурсивный по любой структуре,
   игнорируются только дот-папки, `node_modules`, `target`
   (код: `storage/files.rs:202`).
2. **Коллекция = имя документа.** Проекция каналов ключуется базовым именем
   документа с `type: channel`, без папки (следствие починки фантомных
   каналов, DEVLOG 09.08.2026).
3. **Медиа = базовое имя.** Wikilink `[[img.jpg]]` резолвится поиском по
   имени, при нескольких совпадениях побеждает ближайшее к корню
   (код: `media_refs::resolve_basename_under`).
4. **Запись — в корень.** Все новые файлы (карточки из клиппера, карточки из
   приложения, новые документы коллекций) создаются как `root/<имя>.md`
   (код: `domain/vault.rs:58`, `commands/channels.rs:231` — fallback
   `block_path`, `bin/native_host.rs:750`).

Раскладка `Collections/Cards/Media` — конвенция разового миграционного CLI
(`migrate-vault-layout`), а не контракт: чтение её не требует, запись её не
поддерживает.

## Часть 1 — Подключение папки

### 1.1 Пустая папка

**Прогон:** открывается корректно, ноль блоков, стабильна на переоткрытии.
**Проблема:** только активационная — пустая лента без подсказок
([AUDIT_ACTIVATION.md](AUDIT_ACTIVATION.md), шаг 3).
**Целевое:** онбординг-состояние; бэкенд менять не нужно.

### 1.2 Плоская структура (legacy)

**Прогон:** карточки, медиа рядом, документ коллекции в корне — всё
индексируется, превью `ready`, переоткрытие стабильно.
**Проблема:** нет.
**Целевое:** без изменений; плоская структура остаётся полноправной.

### 1.3 Каноничная структура `Collections/Cards/Media`

**Наблюдение:** читается полностью (реальное хранилище пользователя,
1095 медиа в `Media/`). Но см. 2.1 — запись эту структуру не поддерживает.

### 1.4 Произвольная вложенность

**Прогон:** `Cards/Deep/note.md` и `Cards/note.md` живут одновременно, слаги
разные, конфликтов нет.
**Проблема:** нет — для карточек. Для коллекций см. 3.2.
**Целевое:** явно зафиксировать в SPEC_STORAGE, что вложенность карточек —
поддерживаемый случай (сейчас это работает, но нигде не обещано).

### 1.5 Обычный Obsidian-vault без Mine-структуры

**Прогон:** три заметки (без frontmatter; с Obsidian-frontmatter без Mine-полей;
вложенная) — все стали implicit articles, превью `ready`, `.obsidian/`
проигнорирован, wikilink между заметками цел. Контракт
`SPEC_OBSIDIAN_MARKDOWN_COMPAT` фактически выполняется.
**Проблема:** одна, но чувствительная: Mine начнёт **писать** в этот vault
(`Mine Collections` в frontmatter при связывании, новые файлы в корень). Для
пользователя, подключившего рабочий Obsidian-vault «посмотреть», это
неожиданные правки живых заметок.
**Целевое:** режим уважения к чужому vault: при первом связывании карточки из
implicit-article с коллекцией — однократное подтверждение «Mine добавит поле
в frontmatter этой заметки». Плюс A2.1 из аудита активации (подтверждение
непустой папки) закрывает вход в сценарий.

### 1.6 Гигантская или чужая папка (`~/Documents`, весь `~`)

**Код:** рекурсивный скан без порога и подтверждения; таймаут не ограничен.
**Проблема:** один клик превращает весь архив в «пространство», derived
строится на тысячи файлов; отмены нет.
**Целевое:** A2.1 (подтверждение с фактами) + мягкий порог: свыше N тысяч
файлов — предупреждение о времени и объёме до начала индексации, а не после.

### 1.7 Папка с чужим `.mine/vault-id` (вторая машина, копия)

**Код:** `vault-id` синхронизируется вместе с папкой; derived store у каждой
машины свой (`vaults/<id>/`). Это спроектированное поведение: две машины,
один vault, независимые кэши.
**Проблема:** ручная **копия** папки (не синхронизация) несёт тот же id —
две разные папки делят один derived store; открытие копии молча
переиспользует чужой индекс до реконсиляции.
**Целевое:** при `select_vault` сверять сохранённый путь derived-записи с
фактическим: если id знаком, но путь другой и старый путь жив — это копия;
предложить «форк» (новый id) или «переезд» (обновить путь). Сейчас различия
между переездом и копией нет.

### 1.8 Повторное подключение той же папки

**Прогон:** идемпотентно, счётчики совпадают, дубликатов нет.
**Проблема:** нет.

## Часть 2 — Раскладка и её дрейф

### 2.1 Новые файлы пишутся в корень

**Код:** все три пути записи (клиппер, карточки из приложения, новые
коллекции) кладут файлы в корень. После `migrate-vault-layout` хранилище
начинает дрейфовать обратно к плоскому: свежие клипы — в корне, старые — в
`Cards/`.

**Проблема:** пользователь, попросивший структуру, получает её ровно до
первого клипа. Файловая опрятность — часть ценности продукта.

**Целевое:** контракт целевых папок записи. Минимальный вариант: если в корне
есть `Cards/` и `Media/` (или заданы в настройках пространства), новые
карточки и медиа пишутся туда; коллекции — в `Collections/`. Плюс
опциональная фоновая «уборка» — предложение перенести накопившиеся корневые
файлы по папкам тем же smart-rename путём (с переписыванием ссылок), а не
внешним CLI. Сам CLI остаётся для разовой миграции.

### 2.2 Разовая миграция vs жизнь после неё

**Код:** `migrate-vault-layout` — ручной, однократный, вне приложения.
**Проблема:** то, что CLI создал, ничем не поддерживается (см. 2.1); а сам
CLI недоступен обычному пользователю.
**Целевое:** после реализации 2.1 — кнопка «Организовать пространство по
папкам» в Settings → Spaces, использующая ту же логику; CLI — для
разработчиков.

## Часть 3 — Дубликаты имён

### 3.1 Карточки с одним именем в разных папках

**Прогон:** `Cards/note` и `Cards/Deep/note` сосуществуют; слаг включает
путь. Wikilinks по имени `[[note]]` при этом становятся неоднозначными —
резолв выберет одну из карточек по правилу ближности.
**Проблема:** умеренная — сами карточки целы, но связи могут указать не туда.
**Целевое:** при индексации фиксировать неоднозначные wikilink-цели в
диагностику (по образцу `vault_conflicts`) и показывать в том же баннере;
разрешение — квалификация ссылки путём, как в Obsidian.

### 3.2 Коллекции с одним именем в разных папках

**Прогон:** `Collections/Канал.md` и `Collections/Sub/Канал.md` схлопнулись в
одну проекцию `Канал` — источник и проекция разошлись (аудит-CLI сам
зафиксировал mismatch).

**Проблема — самая острая в документе.** Инвариант «имя документа коллекции
уникально, потому что файловая система не даст двух одинаковых имён»
(DEVLOG 09.08.2026) держится только в пределах одной папки; подпапка его
ломает. Дальше возрождается класс NSFV-бага: операции, пишущие «в документ,
чьё имя совпадает с тегом», находят **два** документа; реордер и переименование
становятся недетерминированными или отклоняются staged-мутацией целиком —
для пользователя это «сортировка снова не сохраняется», без какого-либо
сообщения.

**Целевое:** сделать конфликт имён коллекций явным состоянием: при
реконсиляции два живых документа с одним именем → запись в диагностику,
баннер с показом обоих путей и действием «переименовать один из них»;
мутации коллекции при живом конфликте — запрещены с внятной ошибкой, а не
недетерминированы. Плюс тест на «коллекция в подпапке» в реконсиляции.

### 3.3 Медиа с одинаковым базовым именем

**Код:** побеждает ближайший к корню файл, молча.
**Проблема:** после ручной раскладки медиа по подпапкам один загруженный
позже `image.jpg` в корне перехватывает все старые ссылки `[[image.jpg]]`.
**Целевое:** та же диагностика неоднозначности, что в 3.1; при записи новых
медиа клиппером — суффикс при коллизии базового имени по всему хранилищу
(сейчас проверяется только целевой каталог записи).

## Часть 4 — Приёмочный инструмент лжёт на папках

**Прогон:** `cold-space-audit` на хранилище с единственной коллекцией
`Collections/Канал.md` падает с `collection source/projection mismatch:
source_only=["Collections/Канал"], projection_only=["Канал"]` — инструмент
сравнивает пути, проекция ключуется именами.

**Проблема:** приёмка холодного открытия непроходима для любой каноничной
(же!) раскладки — то есть инструмент качества не покрывает главный
поддерживаемый случай. Реальная приёмка A5 проходила на плоском `Тест`.

**Целевое:** привести аудит к правилу идентичности №2 (сравнивать имена,
предупреждать о дублях путей) и добавить фикстуру с папочной раскладкой в
`test:cold-space`. Это предусловие для честной приёмки всего остального в
этом документе.

## Часть 5 — Перемещения и переименования

### 5.1 Переименование в приложении

**Код:** канонический smart-путь: `.md`, Mine-owned медиа, wikilinks по
хранилищу, перенос производных. Контракт закреплён.

### 5.2 Внешнее переименование при работающем приложении

**Код:** watcher склеивает Remove+Create в rename по `body_hash`; derived
сохраняются; чужие файлы не переписываются.

### 5.3 Перенос `.md` между папками при закрытом приложении

**Прогон:** `Cards/note.md` → `note.md`: слаг сменился (`Cards/note` →
`note`) — для системы это смерть одной карточки и рождение другой.
Membership выживает (он по имени в `Mine Collections`), но производные
(превью, позиция, любое slug-ключёванное состояние) сбрасываются и
перестраиваются.

**Проблема:** тихая потеря производных при законной пользовательской операции
«навёл порядок в Finder при закрытом приложении». Не потеря данных, но
внезапные «полёты» карточек и повторная генерация превью.

**Целевое:** распространить rename-детекцию по content hash с watcher-пути на
холодную реконсиляцию: пропавший путь + появившийся путь с тем же
`body_hash` = перенос, а не delete+create. Механика хэшей уже есть; нужен
только матчинг в `reconcile_vault`.

### 5.4 Перенос целой подпапки

Следствие 5.3, помноженное на объём: все слаги внутри меняются. Целевое
поведение то же — матчинг по хэшу делает перенос папки дешёвой операцией.

## Часть 6 — Хранилище пропало

### 6.1 Между запусками (папка удалена/переименована/на отключённом диске)

**Код:** `get_vault_path` проверяет `is_dir()`; при провале **молча стирает
сохранённый путь** и возвращает `None` — пользователь видит девственный
VaultPicker (`commands/vault.rs:129`). Ни причины, ни старого пути, ни
предложения найти папку.

**Проблема:** для пользователя неотличимо от потери данных. Особенно жестоко
с внешним диском: диск воткнут обратно — а привязка уже стёрта.

**Целевое:** состояние «пространство недоступно»: показать последний путь,
кнопки «Найти папку» (переоткрытие с тем же vault-id — derived выживает),
«Создать новое», «Забыть». Привязку не стирать до явного «Забыть».

### 6.2 Во время работы

**Код:** watcher копит ошибки до порога восстановления; UI о смерти корня не
узнаёт — лента продолжает показывать последний снапшот, операции записи
начнут падать по одной.

**Проблема:** зомби-состояние: выглядит живым, реально мёртво.

**Целевое:** явный сигнал «корень недоступен» от watcher/реконсиляции к
фронту → тот же экран, что в 6.1, поверх приложения.

### 6.3 Переезд хранилища на новый путь

**Код:** выбор новой локации той же папки читает синхронизированный
`.mine/vault-id` → derived переиспользуется. Работает.
**Оговорка:** список `known_vaults` хранит старый путь как отдельную мёртвую
запись; клиппер может целиться в неё.
**Целевое:** при открытии знакомого id по новому пути — обновлять запись
`known_vaults`, а не добавлять вторую.

## Часть 7 — Битые и чужие данные

### 7.1 Сломанный frontmatter

**Прогон:** `type: [broken yaml` → карточка живёт как implicit article с
`index_warning = malformed_frontmatter`, превью `ready`. Один битый файл не
валит ничего вокруг (инвариант «per-file failure» выполняется).
**Целевое:** warning уже показывается в Detail; достаточно.

### 7.2 `.md` вовсе без frontmatter

**Прогон:** implicit article, `ready`. Соответствует контракту compat-спеки.

### 7.3 Карточка ссылается на отсутствующее медиа

**Прогон:** превью `failed: browser_decode_required`, карточка остаётся в
ленте с fallback-заглушкой, Detail показывает «No media / ImageOff».
**Проблема:** формулировка причины врёт: медиа не «требует браузерного
декодирования», его **нет**. Диагностика сливает два разных состояния.
**Целевое:** отдельный `preview_error = missing_source` (код ошибки уже
существует в enum) и текст в Detail «файл “x.jpg” не найден в хранилище» с
кнопкой перевыбора файла.

### 7.4 Медиа-сироты без `.md`

**Код:** в ленту не попадают; Settings → Orphans даёт batch promote/delete.
Работает; единственное — пользователь должен сам догадаться туда зайти.
**Целевое:** счётчик сирот в статистике пространства как точка входа.

### 7.5 Не-медиа мусор (`.DS_Store`, чужие форматы)

**Код:** игнорируется скраном (только `.md` индексируются, медиа — по
ссылкам). Достаточно.

## Часть 8 — iCloud

### 8.1 Конфликтные копии (`имя 2.md`)

**Код:** `detect_icloud_conflict` при реконсиляции → `vault_conflicts` →
`VaultConflictsBanner` с разрешением. Спроектировано и реализовано.

### 8.2 Dataless-файлы (выгруженные iCloud)

**Код:** для видео действует байтовый потолок автовоспроизведения, читающий
размер без скачивания; но чтение **изображений** для превью и открытие
оригинала в Detail форсируют скачивание без индикации; исходная реконсиляция
по метаданным дешёвая (stat не скачивает).
**Проблема:** первое открытие большого выгруженного пространства = массовая
загрузка из iCloud без прогресса и без возможности отказаться.
**Целевое:** распознавать dataless (`NSURLUbiquitousItemDownloadingStatus`
или суррогат по `st_blocks = 0`), показывать состояние «в облаке» на карточке
и качать превью по требованию/по видимости, а не всем скопом.

### 8.3 NFC/NFD имена

**Код:** нормализация на файловых границах по SPEC_IDENTITY_ROBUSTNESS
(`unicode-normalization` в зависимостях, боевое использование в слагах).
Считаю закрытым; регрессы ловить существующими тестами идентичности.

## Часть 9 — Несколько пространств

**Код:** `known_vaults` в общем конфиге; переключатель с pinned-действиями;
клиппер выбирает пространство в попапе; фантомные каналы выметаются
реконсиляцией; derived изолирован по vault-id. Прогон переключения покрыт
браузерным cold-space гейтом.
**Оговорки:** мёртвые записи путей (6.3) и отсутствие «Забыть» с чисткой
derived (место на диске копится).
**Целевое:** «Remove from the list» дополнить опцией «также удалить локальный
кэш этого пространства» с указанием размера.
