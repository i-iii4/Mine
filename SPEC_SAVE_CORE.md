# Общее ядро Mine: правила и сценарии сохранения

Related documents: [PRINCIPLES.md](PRINCIPLES.md) | [ARCHITECTURE.md](ARCHITECTURE.md) | [PLAN.md](PLAN.md) | [SPEC_BLOCK.md](SPEC_BLOCK.md) | [SPEC_DOMAIN.md](SPEC_DOMAIN.md) | [SPEC_STORAGE.md](SPEC_STORAGE.md) | [SPEC_CLIPPER.md](SPEC_CLIPPER.md) | [SPEC_ONBOARDING.md](SPEC_ONBOARDING.md) | [SPEC_VAULT_LIFECYCLE.md](SPEC_VAULT_LIFECYCLE.md) | [SPEC_MOBILE.md](SPEC_MOBILE.md) | [SPEC_AI_ACCESS.md](SPEC_AI_ACCESS.md)

## Статус и границы решения

Архитектура принята пользователем 31.08.2026: одно переносимое Rust-ядро
правил и сценариев, нативный и браузерный исполнители, тонкие платформенные
мосты. Приоритет — корректность, простота дальнейшего развития и отсутствие
копий правил, а не минимальная стоимость переноса.

**SC0 начат по отдельной отмашке пользователя.** Выполняются инвентарь,
контракт и эксперименты на одноразовых папках. SC1–SC7 не начаты и зависят
от закрытия барьера безопасности SC0. План находится в
[PLAN.md](PLAN.md#save-core-plan).

Этот документ задаёт целевую архитектуру. Он не утверждает, что уже созданы
новые крейты, работает WASM-сборка или устранены дефекты клиппера. Контракт
конкурентной браузерной записи требует отдельного закрытия на SC0; до этого
нельзя считать файловый интерфейс окончательно определённым.

## Цель

- Правила Markdown, имён, коллекций и связей имеют одну реализацию.
- Порядок сохранения, трактовка ошибок и восстановление определены одним
  сценарием, а не отдельно в JavaScript, native host и приложении.
- Расширение сохраняет без установленного Mine; установленный нативный
  компонент работает и при закрытом приложении.
- Новая точка входа передаёт подготовленный материал существующему сценарию,
  не создавая собственный формат или алгоритм сохранения.
- Исходные Markdown и медиа остаются читаемыми вне Mine. SQLite и превью —
  восстанавливаемые представления, не условие успешной записи исходников.

## Рассмотренные варианты

Критерии: автономность без установки Mine, одна реализация правил, сохранение
возможностей нативного пути и развитие существующих клиентов. Стоимость
первоначального переноса не является критерием выбора.

| Вариант | Соответствие критериям | Отклонение |
|---|---|---|
| Общее Rust-ядро + два исполнителя — принято | Автономность, общие правила, нативные возможности | Ограничения браузерного файлового API остаются явными |
| Только браузерный исполнитель сохранения | Автономность, один путь внутри расширения | Ослабляет нативную публикацию файлов; само по себе не объединяет правила desktop/iOS |
| Независимые реализации + общие тестовые данные | Сохраняет оба режима; тесты обнаруживают расхождения | Изменение правил приходится повторять в нескольких реализациях |
| Только нативный исполнитель | Общие системные возможности | Требует установленного компонента и нарушает О1 онбординга |

## От чего переходим

Проверено по исходникам на момент принятия решения:

| Место | Текущее устройство | Что меняет переход |
|---|---|---|
| `extension/lib/standaloneVault.js` | Собственные сериализация, выбор имён и запись | Правила переходят в ядро; остаются браузерные операции |
| `src-tauri/src/bin/native_host.rs` | Смешаны протокол, подготовка материала, сохранение и индексирование | Протокол вызывает общий сценарий через нативного исполнителя |
| `extension/lib/standaloneVault.test.ts` | Ожидания скопированы из Rust, но тест исполняет только JS | Один набор входов и эталонов реально проверяет native и WASM |
| `domain/vault.rs` | В `detect()` есть проверка диска, несмотря на описание pure logic | Состояние диска собирает исполнитель, ядро получает факты |
| `core-ffi/src/lib.rs` | FFI-слой содержит сканирование/индексирование | Общие операции принадлежат нативному сервису, FFI только адаптирует вызов |

Уже наблюдается расхождение формата: standalone пишет `type` и `title`,
новый нативный путь карточек не пишет `type` и использует правила заголовка
из [SPEC_DISPLAY_TITLE.md](SPEC_DISPLAY_TITLE.md). Скопированные тесты не
доказывают равенство реализаций. Также подтверждены цикл выбора папки из
оверлея и смешение ошибки связи с отсутствием приложения.

Причина конкретного сбоя соединения в установленной связке Dia/Mine этим
решением не объявляется найденной: её воспроизведение входит в SC4.

## Границы компонентов

Названия ниже обозначают целевые компоненты, не существующие команды или API.
Ядро выделяется в самостоятельный крейт `mine-core`. Конкретные пути новых
пакетов фиксируются в SC1; существующая структура проекта пока не меняется.

```text
                  mine-core: один исходный Rust-код
                     /                       \
            нативная сборка                 WebAssembly
                   |                            |
         нативный исполнитель          браузерный исполнитель
                   |                            |
        desktop / native host /        автономное расширение
        iOS / существующие CLI-вызовы
```

Это переиспользование кода в разных процессах, не единый сервер и не
глобально единственный процесс записи в пользовательскую папку.

| Компонент | Отвечает за | Не содержит |
|---|---|---|
| `mine-core` | Модель документа, сериализация, относительные пути, имена, связи, валидация; решения о шагах сохранения и восстановления | Tauri, браузерные API, прямой доступ к диску, SQLite, сеть, системные диалоги |
| Нативный исполнитель | Системный файловый доступ, подготовка медиа, публикация, хранение состояния операции; наблюдение/индексация отдельными сервисами | Другой сериализатор или собственные правила карточки |
| Браузерный исполнитель | File System Access, разрешения, IndexedDB, загрузки и жизненный цикл service worker | Копия Rust-правил в JS, догадки об установке приложения |
| Мосты Tauri IPC / Native Messaging / UniFFI / WASM | Преобразование вызовов и типов, проверка границы доверия, передача результата | Самостоятельная бизнес-логика сохранения |
| UI и извлечение контента | Получение материала страницы/Share Sheet, выбор пользователя, отображение состояния | Владение форматом файлов или прямой запуск альтернативного сохранения после ошибки |

Ядро получает состояние пространства, результаты операций, время и случайные
значения как входные данные. Оно не получает абсолютные системные пути и не
вызывает `exists`, `is_dir`, сетевой клиент или часы самостоятельно.

Общий сценарий возвращает конкретные необходимые действия и принимает их
результаты. Не вводятся универсальный workflow-движок, шина событий,
плагинная платформа или постоянно работающий сервис ради этого разделения.
Медиа передаётся потоками/ссылками на подготовленные ресурсы; крупные файлы
не должны целиком копироваться через WASM или JSON ради унификации.

## Контракт операции

Следующие сущности — проектные понятия; их точные типы, поля и версии
закрываются на SC0 и генерируются для потребителей из Rust на SC1.

| Сущность | Обязательный смысл |
|---|---|
| Запрос сохранения | Подготовленный контент и намерение пользователя; режим захвата не становится полем `type` карточки |
| Привязка пространства | Конкретная разрешённая папка, её раскладка и идентичность; не просто совпадающее отображаемое имя |
| Контекст операции | Идентификатор повтора, выбранный исполнитель, пространство и набор поддерживаемых возможностей |
| План записи | Относительные целевые пути, подготовленные исходники, необходимые проверки и порядок публикации |
| Результат | Подтверждённый commit, подтверждённое отсутствие commit либо неопределённый исход с возможностью проверки |

Инварианты:

1. Пространство и исполнитель фиксируются до начала записи. Смена текущей
   папки в UI не перенаправляет уже начатую операцию.
2. Повтор того же запроса использует ту же идентичность операции. Намеренное
   новое сохранение — новая операция; дедупликация по URL не подменяет её.
3. Таймаут или разрыв соединения не доказывает отказ записи. Нельзя запускать
   второй способ сохранения, пока исход первого не установлен.
4. Пользователь получает успех только после подтверждения исходных файлов.
   Обновление SQLite и превью выполняется после этого; их ошибка не превращает
   состоявшееся сохранение в предложение создать ещё одну карточку.
5. Известный конфликт имён не перезаписывается. Новое имя выбирает ядро после
   обновления фактов о папке; нативный исполнитель дополнительно обеспечивает
   системный отказ при занятом имени в момент публикации.
6. Состояние восстановления не хранится только в памяти popup/worker/host.
   Его владелец, размещение, версия, срок жизни и поведение при потере
   фиксируются на SC0 отдельно от удаляемого индекса и кэша превью.
7. Идентификатор операции не становится служебным ID карточки во frontmatter.
   Он не меняет filename-first identity, имена файлов или пользовательскую
   структуру папок без отдельного согласования.
8. Очистка удаляет только доказанно принадлежащие операции промежуточные
   данные. Она не удаляет чужой файл с совпавшим именем и не уничтожает
   единственную копию материала с неопределённым исходом.

Ошибки типизированы: неподдерживаемая возможность, недоступное пространство,
нет разрешения, конфликт, ошибка подготовки, ошибка публикации, несовместимый
протокол и неопределённый исход различаются. UI не выводит причину из текста
исключения и не сводит всё к `ok: false`.

### SC0: проект версионированной границы

Это минимальный проект контракта для SC1, не уже доступные API. Набор
файловых гарантий browser и доказательства принадлежности опубликованного
файла остаются открытыми до барьера ниже. Состояния транспорта не входят
в модель Markdown, а файловые handles не передаются в pure core.

| Тип | Поля и ограничения |
|---|---|
| `SaveRequestV1` | `operation_id`, `mode: start/resume`, `binding_id`, `executor_id`, `saved_at`, `intent`, подготовленный контент и `assets[]`; ресурс задаётся `resource_id` исполнителя, не массивом байтов в JSON/WASM |
| `SpaceBinding` | Непрозрачный `binding_id`, проверенная идентичность папки, snapshot раскладки; абсолютный путь/handle хранит исполнитель. Копия vault с тем же marker не автоматически та же папка |
| `SaveResultV1` | `operation_id`, `source: not_committed/committed/unknown`, подтверждённые пути, `durability: confirmed/unknown/not_applicable`, `projection: pending/ready/failed/not_reported`, типизированная ошибка |
| `ExecutorCapabilitiesV1` | Версия протокола, `save_operation_v1`, `operation_lookup_v1`, транспорт `pending_uploads_v1`, media-возможности; гарантии `atomic_no_clobber`, `complete_file_publication`, `durable_flush`: каждая `supported/unsupported/unverified` |
| `OperationRecordV1` | Версия, ID и fingerprint неизменяемого запроса, сохранённый запрос, привязка, исполнитель, фаза, цели `{relative_path, size, sha256, staged_resource, publication_state, ownership_evidence?}`, результат и при наличии `legacy_upload_id` |

`app_installed` не существует: связь, совместимость, разрешение и выбранная
папка — отдельные состояния. Отсутствие ответа не является проверкой установки.

`source=committed` означает подтверждённую публикацию полного Markdown
и обязательных медиа. Ошибка синхронизации каталога **после** успешной
публикации означает `committed + durability=unknown`, не разрешение удалить
медиа как при отсутствии карточки. Если наблюдатель не знает, произошла ли
публикация, результат `unknown`. `not_committed` относится к карточке;
частично опубликованное медиа отдельно остаётся в записи операции до
доказанной очистки. Индекс и превью не определяют эти состояния.

Журнал операции отделён от перестраиваемого индекса и кэша. Его владелец —
исполнитель: отдельное app-state хранилище native и extension-origin
IndexedDB browser. Не требуется новый экран или пользовательская папка для
журнала. Конкретные пути native, схема IDB и доказательства публикации
фиксируются до закрытия SC0; сейчас они не определены и их нельзя
объявлять готовыми на основании этой таблицы.

До первого изменения исходников записываются неизменяемый запрос, привязка,
ссылки на переживающий перезапуск материал и план целей. Повтор того же ID
с другим fingerprint отклоняется. `resume` без записи означает неизвестный
исход, не новый `start`. После публикации сохраняется компактный результат;
повтор возвращает его после проверки состояния. Завершённая запись может
оставаться без дублирующего payload; незавершённую запись и единственную
копию материала нельзя удалять только по возрасту. Удаление самого browser
storage не является гарантированно восстанавливаемым событием.

Миграция старого staging отделена от протокола сохранения. Новый host
связывает `pre_uploaded_id` с операцией до публикации; старая capability
не означает новый контракт повторов. Manifest без receipt импортируется
как неподтверждённый, а не как доказанный мусор или успех. Уже удалённый
payload восстановить из manifest невозможно. До включения перехода нужно
проверить конкурентный старый host и исключить гонку с возрастной очисткой.

## Файловые гарантии и обязательный барьер SC0

Два исполнителя не имеют одинаковых системных гарантий. Нативный
`storage/files.rs::write_new_atomically` публикует готовый временный файл
без замены занятого пути. Браузерный `getFileHandle({create:true})` возвращает
существующий файл либо создаёт новый; это не атомарное create-if-absent.
Создание handle также может сделать видимым пустой конечный файл до записи.
[File System Standard](https://fs.spec.whatwg.org/#api-filesystemdirectoryhandle-getfilehandle).

Очередь внутри расширения устраняет его собственные гонки. Она не блокирует
другой профиль, Mine, Obsidian или синхронизацию. Браузерные блокировки и WASM
не дают автоматически общесистемную защиту от изменения файла извне.
[Граница внешних изменений](https://fs.spec.whatwg.org/#file-system-entry).

До реализации общего файлового интерфейса SC0 обязан зафиксировать:

- Точку commit отдельно для native и browser, в том числе окно между записью
  медиа, Markdown и подтверждением в журнале.
- Восстановление после остановки на каждом шаге, потерянного ответа,
  отсутствующего журнала и перезапуска браузера/host.
- Результат конкуренции с внешним процессом: что предотвращается, что только
  обнаруживается и какие случаи платформа не позволяет гарантировать.
- Профили возможностей исполнителей, включая no-clobber и публикацию без
  промежуточного пустого файла. Неподдерживаемая гарантия не объявляется
  поддерживаемой ради общего интерфейса.
- Контракт поддерживаемого автономного режима: он обязан сохранять без Mine,
  но строгую защиту общей папки от любой внешней гонки нельзя обещать на
  основании текущего API.
- Формат/хранилище подтверждений, миграцию `pending_uploads_v1`, очистку и
  проверку результата после потери локального служебного состояния.

SC0 заканчивается воспроизводимыми экспериментами на одноразовых папках и
таблицей гарантий. Если для безопасности нужны новые правила имён, отдельная
папка приёма, обязательный helper или ослабление требования сохранности,
это **новое продуктовое решение**, а не разрешённая деталь реализации.
Его нужно отдельно согласовать; зависимые этапы не стартуют до решения.
Принятие общей архитектуры не означает принятия такого изменения.

### SC0: протокол проверок

Проверенные результаты и команды: [отчёт SC0](docs/sc0-save-safety.md).

Пробы характеризуют текущую реализацию, а не объявляют обнаруженный дефект
допустимым контрактом. Никакая проба не использует пользовательское хранилище
или действующий профиль браузера. Нативные тесты используют `tempfile`,
браузерный стенд — отдельные временные профиль и папку с тестовыми маркерами.

| Проба | Детерминированная граница | Что проверяется |
|---|---|---|
| N1 | Два native writer начинают публикацию через barrier | Ровно один полный файл; занятый путь не изменяется |
| N2 | Два вызова финализации одного pending upload | Есть ли подтверждение ранее опубликованного медиа или создаётся дубликат |
| N3 | Настоящий host завершил save, ответ потерян, повторён тот же ID | Сохранился ли результат операции после удаления staging |
| N4 | Воссоздано файловое состояние после Markdown commit до cleanup | Узнаёт ли host уже состоявшуюся операцию при повторе |
| N5 | Legacy upload и занятое имя в `Media/` | Не подменяет ли rename чужое медиа |
| B1 | Получен настоящий OS-directory handle; создан file handle, stream ещё не закрыт | Видит ли внешний процесс пустой конечный файл |
| B2 | После проверки отсутствия внешний процесс создаёт файл через create-new | Сохраняются ли внешние байты после browser write/close |
| B3 | Browser exclusive stream открыт; пишут второй browser stream и внешний процесс | Различаются ли внутрибраузерная и общесистемная блокировки |

N4 — воспроизведение состояния диска, не проверка настоящим убийством
процесса. Ошибку fsync после публикации нельзя считать воспроизведённой без
управляемой точки отказа. B1–B3 используют File System Access выбранной
системной папки, не OPFS и не mock; внешний writer работает отдельным
процессом. Между шагами явные барьеры, случайные задержки не заменяют гонку.
Результаты включают версии, команды и фактические байты. Локальная
probe-страница не заменяет сквозную проверку origin расширения на SC6.

Проверка исходников выявила противоречие старого screenshot-контракта:
popup повторяет тот же `pre_uploaded_id`, но `PendingUploadGuard` удаляет
staging после любого штатного возврата host. Manifest не содержит commit
receipt. Поэтому `pending_uploads_v1` означает транспорт staging, а не
доказанную идемпотентность; это нужно исправить при переносе, а не сохранить.

## Подключение, пространство и пользовательский опыт

Протокол связи принадлежит мосту. Он сообщает совместимость версий,
возможности и состояние подключения независимо от выбранной папки. Успешный
ответ без настроенного пространства означает «компонент доступен, выберите
папку», а не «приложение отсутствует».

Целевой установочный путь: первый запуск Mine регистрирует поставляемый
компонент и разрешённые идентификаторы расширения для поддерживаемых
браузеров; последующие запуски проверяют регистрацию и версию. Production ID
стабилен, dev ID закреплён ключом; пользователь не вводит ID вручную.
Факт скачивания `.dmg` или копирования `.app` не является сигналом связи.
Отсутствие ответа не доказывает отсутствие приложения. Механизм регистрации
и запуска отдельного процесса описан в
[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging);
стабильный dev ID — в [manifest key](https://developer.chrome.com/docs/extensions/reference/manifest/key).

Регистрация файла на диске и подтверждённое соединение — разные статусы.
Настройки показывают последний результат проверки с его актуальностью,
а не называют существующий манифест доказательством соединения. Несовместимый
старый компонент не должен молча получать новый формат команд.

| Ситуация | Целевое поведение |
|---|---|
| Расширение без приложения | Доступное действие выбора папки открывает окно/страницу расширения; разрешение запрашивается по пользовательскому жесту |
| Выбор начат из оверлея страницы | Черновик сохраняется, открывается extension-origin setup, после выбора человек возвращается к материалу |
| Потерян доступ к папке | Восстановление разрешения на эту папку; не обязательная загрузка Mine |
| Компонент доступен, папка не выбрана | Выбор пространства; связь не объявляется сломанной |
| Mine установлен, но связь не работает | Причина и восстановление/повтор проверки; не утверждение «приложение не установлено» |
| Mine установлен после автономных сохранений | Предлагается явно подключить ту же папку; если доказать совпадение нельзя, нужен системный выбор, а не сопоставление по имени |
| Приложение закрыто | Сохранение продолжает работать; это сохранение существующей возможности |
| Исход сохранения неизвестен | Материал и контекст операции сохраняются; сначала проверка результата, затем допустимый повтор |

После привязки пространства доступный совместимый native executor можно
выбрать для новой операции. Само обнаружение компонента не меняет папку и
не переподключает начатую операцию. При первоначальной настройке native
недоступен — пользователь может выбрать автономную папку. При неисправности
ранее выбранного native-пути скрытого переключения нет: сначала диагностика
или явный выбор пользователем другого доступного пути к подтверждённой папке.

## Совместимость и границы переноса

- Сохраняются действующие контракты Markdown, заголовков, коллекций,
  filename-first identity и раскладки; чтение старых файлов остаётся
  совместимым. Перенос ядра сам по себе не запускает массовую миграцию vault.
- Нативные скриншоты сохраняют совместимость транспорта `pending_uploads_v1`;
  его текущая очистка не обеспечивает безопасный повтор и подлежит исправлению.
  Большие медиа не заменяются целиком упакованным JSON. HTTP staging остаётся
  деталью транспорта до отдельной проверки необходимости менять его.
- Возможности медиа объявляются явно. Без native некоторые защищённые видео
  недоступны для загрузки, inline-медиа может остаться удалённым согласно О4.
  Ссылка и локально сохранённый файл не выдаются друг за друга.
- Общий нативный исполнитель переиспользуется текущими desktop, host,
  iOS/UniFFI и CLI/MCP там, где у них уже есть соответствующие операции.
  Сохраняются полномочия и ограничения существующих мутаций; читающие вызовы
  остаются без записи, watcher и принудительной реконсиляции.
- Общий сценарий создания не подменяет специфику rename/delete/merge.
  Существующие гарантии их rollback в `source_mutation` сохраняются;
  перенос общих правил не является разрешением упростить эти транзакции.
- Самостоятельная работа через File System Access принимается в Chrome и Dia.
  Фактическая поддержка API и разрешений проверяется в этих браузерах.
  Существующая Safari-интеграция не ломается, но её публичный выпуск и
  автономный режим не добавляются этим планом.
- Публикация в Chrome Web Store, подпись/notarization и расширение общего
  distribution-scope не начинаются автоматически; ограничения
  [SPEC_DISTRIBUTION.md](SPEC_DISTRIBUTION.md) сохраняются.

## Приёмка результата

Архитектура считается реализованной только после SC7:

1. `mine-core` собирается для native и браузерного WASM без Tauri, SQLite,
   системного файлового доступа и сетевых зависимостей. JS использует
   собранный артефакт этого ядра, а не его вручную переписанную копию.
2. Одни входные данные и эталоны проверяются нативной сборкой и настоящим
   WASM в браузере: формат, Unicode, коллизии имён, вложенные целевые папки,
   коллекции, ошибки и переходы восстановления.
3. На реальных исполнителях воспроизведены границы отказов SC0, повтор после
   потери ответа, конкурентная запись, отмена, перезапуск и отсутствие индекса.
   Отчёт различает предотвращённую гонку и только обнаруженное повреждение.
4. Пройдены обе последовательности установки и автономная работа без host,
   закрытое приложение, отозванное разрешение, битый/старый host, отсутствующее
   пространство и подключение существующей автономной папки в Chrome и Dia.
5. Установка и восстановление проходят без терминала и ручного extension ID;
   видимый результат — файл в выбранной папке и соответствующая карточка в
   Mine, а не только успешный ответ протокола.
6. Нет двух рабочих сериализаторов или двух независимых сценариев сохранения.
   Временные переходные вызовы удалены после перевода всех затронутых клиентов;
   тесты, документация и сборка не ссылаются на удалённый путь.

WASM-мост строится средствами
[wasm-bindgen](https://wasm-bindgen.github.io/wasm-bindgen/); выбор конкретных
версий и сборочных команд проверяется при SC1/SC3. Документ не вводит
несуществующие команды в рабочий цикл проекта.
