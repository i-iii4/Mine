# SPEC_AI_ACCESS

Related documents: [ARCHITECTURE.md](ARCHITECTURE.md) | [SPEC_SEARCH.md](SPEC_SEARCH.md) | [SPEC_STORAGE.md](SPEC_STORAGE.md) | [SPEC_VAULT_LIFECYCLE.md](SPEC_VAULT_LIFECYCLE.md) | [SPEC_SAVE_CORE.md](SPEC_SAVE_CORE.md)

Доступ AI-агентов к материалам пространства — чтение и безопасные мутации.
Статус: **принято 27.08.2026**, реализация начата (первым — читающее ядро).

## Зачем

Главная ценность интерфейса — производные данные, которых в сырых файлах
нет: гибридный поиск (FTS5 плюс семантические эмбеддинги), модель коллекций,
резолв медиа-ссылок, метаданные карточек. После решения 044
([SPEC_BLOCK.md](SPEC_BLOCK.md)) вид карточки — производное от содержимого;
поля `type` в файлах нет, и интерфейс не должен его изобретать заново.

При этом интерфейс **самодостаточен**: сырое содержимое — тело карточки,
список карточек, пути медиа — отдаётся через него же. У потребителя без шелла
(claude.ai, Desktop, телефон) другого канала нет, а агент с шеллом не обязан
жонглировать двумя способами доступа. «Это можно сделать grep-ом» — не
критерий исключения; критерий — нужна ли операция для работы с материалами
(уточнение 25.08.2026 после возражения пользователя).

## Решение

Принятое разделение переносимого ядра и нативного исполнителя описано в
[SPEC_SAVE_CORE.md](SPEC_SAVE_CORE.md); реализация SC0–SC7 ожидает отмашки.
Перенос сохраняет действующие CLI/MCP-вызовы: чтения не получают побочных
записей, мутации сохраняют существующие guards и dry-run. Новые полномочия
или команды из самого факта появления общего ядра не следуют.

Ядро → CLI → MCP, в этом порядке (обсуждение 24.08.2026):

- читающий API выносится в ядро (Rust, тот же крейт);
- первым слоем — CLI `mine`: дёшево, отлаживаемо, полезно и человеку;
- MCP-сервер — этап 2, тонкий адаптер над тем же ядром (`mine mcp`),
  когда появится потребитель без шелла (claude.ai, Desktop, телефон).
  Совместимость закладывается сейчас: JSON-контракт CLI и есть будущие
  схемы MCP-инструментов.

## Требования: ядро

- **Read-only гарантия.** SQLite открывается в режиме только для чтения;
  никакой записи в индекс, в исходники, в кэш превью. Watcher не поднимается,
  реконсиляция не запускается.
- **Сосуществование с приложением.** Индекс в WAL; читающее подключение не
  блокирует запись работающего приложения и не падает от неё.
- **Свежесть — честная.** Ядро читает то, что индекс успел записать. Если
  приложение не запущено и хранилище менялось извне, данные могут отставать;
  это констатируется, не чинится (реконсиляция — собственность приложения).
- **Выбор пространства.** По умолчанию — `vault_path` из `config.json`
  приложения; любое из `known_vaults` — по флагу. Путь вне известных
  пространств отклоняется с внятной ошибкой.
- **Семантический поиск.** Использует модель fastembed из кэша приложения.
  Модели нет — поиск деградирует до лексической части с пометкой в ответе,
  не падает.

## Требования: CLI `mine`

Отдельный bin target существующего крейта, как `cold-space-audit`.

Подкоманды первой очереди:

| Команда | Назначение |
|---|---|
| `mine spaces` | Известные пространства, активное помечено |
| `mine search <query> [--space P] [--limit N]` | Гибридный поиск, результат с score и слагами |
| `mine collections [--space P]` | Коллекции со счётчиками |
| `mine cards --collection C [--limit N --offset K]` | Карточки коллекции |
| `mine card <slug>` | Полная карточка: frontmatter, body, абсолютные пути медиа |

Согласование с решением 044: в выводе нет поля `type`. Карточка описывается
содержимым — `body`, список медиа с путями, `url` — и производным
`card_kind` («какой карточкой это показывается»), помеченным как derived.
Фильтр «только медиа/только текст» в `mine search`, если появится, работает по
производному виду, а не по несуществующему полю.

Контракт вывода:

- по умолчанию — человекочитаемый текст;
- `--json` — стабильный версионированный JSON (`{"contract": 1, …}`);
  это же будущие схемы MCP-инструментов;
- типизированные коды возврата: 0 успех, 2 неверные аргументы,
  3 пространство недоступно, 4 не найдено;
- ошибки — в stderr, машинный вывод — только в stdout.

## Требования: мутации (27.08.2026)

**Принцип.** CLI никогда не редактирует файл как текст. Каждая мутация:
разбор в типизированную модель → изменение поля модели → сериализация →
атомарная запись с откатом (существующие `source_mutation`,
`write_atomically`). Операции уровня «замени байты» в каркасе не существует —
сломать фронтматтер нельзя тем же способом, каким это нельзя в интерфейсе.

**Инварианты каждой записи:** результат разбирается обратно (round-trip),
иначе отказ; фронтматтер не может исчезнуть или потерять `saved_at`;
экранирование — через `yaml_quote`.

**Операции** — переиспользуют доменные операции приложения, без дублирования:

| Группа | Команды |
|---|---|
| Коллекции | создать, переименовать, удалить; `connect`/`disconnect` карточка↔коллекция |
| Карточки | создать (как вставка), переименовать, удалить (тот же план с медиа, что в UI), merge |
| Фронтматтер | `mine card set/unset title\|description\|url\|author\|source <slug>` — только известные поля |
| Тело | `mine card body <slug>` — чтение; `mine card set-body <slug>` (stdin/файл) — замена целиком |

**Защищённые поля:** `Mine Collections` — только через connect/disconnect;
`file` — только профильными медиа-операциями; `saved_at` неизменяем;
произвольные YAML-ключи писать нельзя.

**Защита тела.** Набор медиа-вставок `![[…]]` до записи обязан совпадать с
набором после; потеря вставки — отказ с перечнем потерянных, сознательное
изменение состава — явный флаг `--allow-media-changes`. Это делает безопасным
основной сценарий «прочитал → перевёл → записал».

**Страховка:** `--dry-run` у каждой мутации (дифф без записи); перед каждой
записью копия прежней версии файла в derived store (не в хранилище — iCloud и
Obsidian её не видят), `mine restore <slug>` возвращает последнюю; чтение
индекс не трогает. Мутации обновляют индекс: структурные операции
(create/rename/delete/merge, коллекции) пишут его транзакционно тем же кодом,
что и приложение, полевые (set/set-body/connect/disconnect/restore)
переиндексируют карточку после записи файла. Файлы остаются источником истины,
watcher приложения видит те же изменения и сходится к тому же состоянию.

**Решение по объёму:** `delete` и `merge` входят в первую очередь — иначе
«всё то же, что в интерфейсе» не выполняется.

**Статус реализации (27.08.2026).** Реализованы: чтение (5 команд), `card set` /
`unset` известных полей (хирургическая правка одной строки фронтматтера,
`yaml_quote` общий с сериализатором), `card body` / `set-body` (фронтматтер
байт-в-байт, защита вставок), `connect` / `disconnect` (единственная дверь к
`Mine Collections`, через `patch_collections_frontmatter`), `restore`
(своп с копией в derived store, один уровень в обе стороны), `--dry-run` у
всех мутаций. Заметка без фронтматтера отклоняет правку полей — CLI не
изобретает метаданные в чужих файлах.

Структурные операции тоже реализованы и переиспользуют inner-функции
приложения (`rename_block_file_inner`, `delete_block_inner`,
`merge_blocks_inner`, `create/rename/delete_channel_inner`), поэтому
инварианты и транзакционность индекса совпадают с UI один в один:

- `mine card create [--title] [--url] [--collection] [--file] [--from]` —
  карточка без поля `type` (решение 044), слаг по правилам приложения,
  раскладка по `layout.json`;
- `mine card rename <slug> <new-name>` — файл и индекс вместе;
- `mine card delete <slug> [--delete-unused-media] [--dry-run]` — тот же план
  медиа, что в UI (dry-run печатает unused/shared); перед удалением текст
  карточки копируется в `cli-backups`, так что `mine restore` возвращает его;
- `mine merge <slug> <slug> […]` — та же композиция, что batch Merge в UI;
- `mine collection create/rename/delete` — страница коллекции и членство в
  карточках обновляются как в приложении.

Подавление watcher-а (`suppress_paths`) в inner-функциях выполняется только
при наличии `AppState` — из CLI-процесса watcher приложения обязан видеть
внепроцессные изменения.

Удаление файлов идёт тем же путём, что в UI: `delete_user_file` перемещает
`.md` и медиа в системную корзину (безвозвратно — только когда корзина
недоступна, например для некоторых iCloud-заглушек). `cli-backups` — второй
слой поверх корзины: `mine restore` возвращает текст карточки одной командой.

Установка: `bun run cli:install` собирает release-бинарник и кладёт его как
`~/.local/bin/mine`. Впереди: MCP (этап 2).

## Требования: MCP (этап 2) — реализовано (27.08.2026)

- `mine mcp` — stdio-сервер в том же бинарнике (JSON-RPC 2.0, по строке на
  сообщение): `initialize`, `ping`, `tools/list`, `tools/call`;
- 19 инструментов повторяют подкоманды CLI один в один; адаптер (`mcp.rs`)
  не содержит доменной логики — каждый вызов собирает argv и проходит через
  `cli::run` с `--json`, поэтому охраны, бэкапы и вывод совпадают с CLI по
  построению;
- тела (`card_set_body`, `card_create.body`) передаются строкой аргумента и
  доезжают до CLI через временный файл и `--from`;
- отказ инструмента (карточка не найдена, охрана сработала) возвращается как
  `isError: true` с текстом stderr; повреждённый вызов (нет обязательного
  аргумента, неизвестный инструмент) — ошибка JSON-RPC `-32602`;
- подключение: `claude mcp add -s user mine -- ~/.local/bin/mine mcp`
  (выполнено 27.08.2026, сервер в user-конфиге) или любой MCP-клиент с
  транспортом stdio; сквозная цепочка «Claude → MCP → mine → хранилище»
  проверена на реальных пространствах.

## Вне объёма

Удалённый доступ и аутентификация, произвольные YAML-ключи, правка файлов вне
известных пространств, «сырые» файловые операции, MCP resources и стриминг.

## Тесты

- интеграционные тесты CLI против фикстурного пространства: каждая
  подкоманда, оба формата вывода, коды возврата, read-only (снимок файлов
  до и после прогона идентичен) — покрыто, включая JSON структурных команд,
  ошибочные пути без побочных эффектов, `--space` для мутаций и восстановление
  удалённой карточки через `restore`;
- поиск без модели эмбеддингов: лексическая деградация с пометкой;
- параллельный прогон с открытым на запись индексом — покрыт: открытое
  соединение второй стороны и удерживаемая write-транзакция, которую CLI
  пережидает по `busy_timeout`.
