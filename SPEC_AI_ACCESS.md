# SPEC_AI_ACCESS

Related documents: [ARCHITECTURE.md](ARCHITECTURE.md) | [SPEC_SEARCH.md](SPEC_SEARCH.md) | [SPEC_STORAGE.md](SPEC_STORAGE.md) | [SPEC_VAULT_LIFECYCLE.md](SPEC_VAULT_LIFECYCLE.md) | [SPEC_SAVE_CORE.md](SPEC_SAVE_CORE.md)

Доступ AI-агентов к материалам пространства — чтение и безопасные мутации.
Статус: **принято и реализовано 27.08.2026**: читающее ядро, CLI `mine` с
мутациями и MCP-адаптер `mine mcp`.

## Зачем

Главная ценность интерфейса — производные данные, которых в сырых файлах
нет: гибридный поиск (FTS5 плюс семантические эмбеддинги), модель коллекций,
резолв медиа-ссылок, метаданные карточек. После решения 044
([SPEC_BLOCK.md](SPEC_BLOCK.md)) вид карточки — производное от содержимого;
поля `type` в файлах нет, и интерфейс не должен его изобретать заново.

При этом интерфейс **самодостаточен**: сырое содержимое — тело карточки,
список карточек, пути медиа — отдаётся через него же. У потребителя без шелла
(claude.ai, Desktop, телефон) другого канала нет, а агент с шеллом не обязан
жонглировать двумя способами доступа. «Это можно сделать grep-ом» — не
критерий исключения; критерий — нужна ли операция для работы с материалами
(уточнение 25.08.2026 после возражения пользователя).

## Решение

Принятое разделение переносимого ядра и нативного исполнителя описано в
[SPEC_SAVE_CORE.md](SPEC_SAVE_CORE.md); CLI create уже использует
`mine_core::save::build_capture` и общие правила имён.
Перенос сохраняет действующие CLI/MCP-вызовы: чтения не получают побочных
записей, мутации сохраняют существующие guards и dry-run. Новые полномочия
или команды из самого факта появления общего ядра не следуют.

Ядро → CLI → MCP, в этом порядке (обсуждение 24.08.2026):

- читающий API выносится в ядро (Rust, тот же крейт);
- первым слоем — CLI `mine`: дёшево, отлаживаемо, полезно и человеку;
- MCP-сервер — этап 2, тонкий адаптер над тем же ядром (`mine mcp`),
  когда появится потребитель без шелла (claude.ai, Desktop, телефон).
  Совместимость закладывается сейчас: JSON-контракт CLI и есть будущие
  схемы MCP-инструментов.

## Требования: ядро

- **Read-only гарантия.** SQLite открывается в режиме только для чтения;
  никакой записи в индекс, в исходники, в кэш превью. Watcher не поднимается,
  реконсиляция не запускается. Поколение индекса берётся то, которое выбрало
  приложение (`existing_selected_index`), без создания, миграции и
  восстановления. Индекс, которого нет, который ещё строится (`ready = 0`)
  или повреждён, чтение называет и отвечает кодом 3: «the index of <путь> is
  not built yet; open the space in Mine to build it» или «… is damaged; open
  the space in Mine to rebuild it». До 13.10.2026 чтение создавало индекс
  пространства, которое приложение ни разу не открывало, и запускало полную
  сверку недостроенного (SPEC_DEEP_AUDIT.md, Е2.21; тест
  `reading_builds_no_index_and_reconciles_nothing` в `cli.rs`). Мутации
  по-прежнему пишут индекс по своим правилам (раздел «Требования: мутации»).
- **Время с поясом.** `saved_at` в выдаче (`card`, `cards`, `search`, JSON и
  текст) идёт с поясом: значение с поясом остаётся как есть, местное время без
  пояса, как его хранят индекс и новые файлы, получает смещение этого Мака в
  тот момент (`saved_at_with_zone`, SPEC_DEEP_AUDIT.md, Е2.22). Файлы не
  меняются.
- **Сборка названа.** `mine --version` печатает версию, сборку
  (`MINE_BUILD_ID`) и коммит программы, а если приложение записало свою
  сборку, и её. Приложение при каждом запуске записывает свою сборку в
  `app-build.json` в папке своих данных. CLI другой сборки, чем приложение,
  на каждом вызове пишет в stderr одну строку «warning: this mine CLI is build
  <версия+сборка> and the Mine app is build <версия+сборка>; reinstall the CLI
  from the app's build (bun run cli:install)»; stdout с JSON остаётся целым.
  MCP называет сборку в `serverInfo.version` (`0.1.0+<12 знаков сборки>`) и
  при расхождении кладёт ту же строку в `instructions` ответа `initialize` и
  вторым текстом в ответ каждого инструмента. До 13.10.2026 CLI устаревал
  незаметно, а MCP всегда называл версию 0.1.0 (SPEC_DEEP_AUDIT.md, Е2.22).
  Расхождением считается другой исходный код, а не другая сборка: приложение
  и CLI из одной рабочей копии собираются с разными возможностями
  (features), и их `MINE_BUILD_ID` не совпадает никогда. Поэтому сравнивается
  отпечаток исходников `MINE_SOURCE_ID` (те же файлы, что у `MINE_BUILD_ID`,
  без возможностей и профиля сборки), который приложение пишет в
  `app-build.json` полем `source_id`. Запись без `source_id` сделана сборкой
  до этого правила, то есть из другого исходного кода, и тоже называется.
  До 13.10.2026 CLI и приложение одного коммита предупреждали на каждом
  вызове (SPEC_DEEP_AUDIT.md, Е2.25).
- **Сосуществование с приложением.** Индекс в WAL; читающее подключение не
  блокирует запись работающего приложения и не падает от неё.
- **Свежесть — честная.** Ядро читает то, что индекс успел записать. Если
  приложение не запущено и хранилище менялось извне, данные могут отставать;
  это констатируется, не чинится (реконсиляция — собственность приложения).
- **Выбор пространства.** По умолчанию — `vault_path` из `config.json`
  приложения; любое из `known_vaults` — по флагу. Путь вне известных
  пространств отклоняется с внятной ошибкой. С 03.10.2026 `vault_path`
  означает пространство видимой вкладки последнего окна вкладок
  ([SPEC_TABS.md](SPEC_TABS.md), В74). CLI работает один вызов и читает его
  при каждом запуске, как прежде; MCP закрепляет пространство по умолчанию на
  всё время своего процесса (раздел MCP).
- **Семантический поиск.** Использует модель fastembed из кэша приложения.
  Модели нет — поиск деградирует до лексической части с пометкой в ответе,
  не падает.

## Требования: CLI `mine`

Отдельный bin target существующего крейта, как `cold-space-audit`.

Подкоманды первой очереди:

| Команда | Назначение |
|---|---|
| `mine spaces` | Известные пространства, активное помечено |
| `mine search <query> [--space P] [--limit N]` | Гибридный поиск, результат со слагом и именем файла |
| `mine collections [--space P]` | Страницы коллекций со счётчиками карточек; пустая страница со счётчиком 0, имя без страницы не выводится |
| `mine cards --collection C [--limit N --offset K]` | Карточки коллекции; имя без страницы отвечает кодом 4 |
| `mine card <slug>` | Полная карточка: frontmatter, body, абсолютные пути медиа; в `collections` только коллекции со страницей |

Коллекция существует только как страница с `type: channel` (решение
пользователя 10.10.2026, [SPEC_COLLECTIONS_OBSIDIAN_LINKS.md](SPEC_COLLECTIONS_OBSIDIAN_LINKS.md),
К1, К2 и К9). Ссылку `Mine Collections` на имя без страницы чтения CLI и MCP
не показывают и не считают; в файле она остаётся. Реализовано 10.10.2026
(PLAN.md, Phase 44).

Согласование с решением 044: в выводе нет поля `type`. Карточка описывается
содержимым — `body`, список медиа с путями, `url` — и производным
`card_kind` («какой карточкой это показывается»), помеченным как derived.
Фильтр «только медиа/только текст» в `mine search`, если появится, работает по
производному виду, а не по несуществующему полю.

Контракт вывода:

- по умолчанию — человекочитаемый текст;
- `--json` — стабильный версионированный JSON (`{"contract": 1, …}`);
  это же будущие схемы MCP-инструментов;
- типизированные коды возврата: 0 успех, 2 неверные аргументы,
  3 пространство недоступно, 4 не найдено;
- ошибки — в stderr, машинный вывод — только в stdout.

**Имя результата поиска (06.10.2026).** Поиск называет результат именем
файла, как список поиска в приложении (решение пользователя от 05.10.2026,
[SPEC_SEARCH.md](SPEC_SEARCH.md), раздел Match Metadata): имя `.md` файла
карточки без папки и без `.md`, то есть последний сегмент слага, то самое
имя, которое меняет `mine card rename`. Текстовый вывод `mine search`
печатает по строке на результат: слаг, табуляция, имя файла
(`Cards/Шуховская башня\tШуховская башня`). В JSON у каждого элемента
`results` есть поле `name` с этим именем. Поле `title` сохраняет смысл
контракта 1: видимый заголовок заметки (H1 или legacy `frontmatter.title`),
`null`, если его нет. Поле `name` добавлено, прежние поля не изменились,
поэтому версия контракта остаётся 1. MCP-инструмент `search` отдаёт тот же
JSON, и его описание называет `name` именем результата. `mine cards` и
`mine card` результатов поиска не показывают и называют карточку как прежде.

## Требования: мутации (27.08.2026)

**Принцип.** CLI никогда не редактирует файл как текст. Каждая мутация:
разбор в типизированную модель → изменение поля модели → сериализация →
атомарная запись с откатом (существующие `source_mutation`,
`write_atomically`). Операции уровня «замени байты» в каркасе не существует —
сломать фронтматтер нельзя тем же способом, каким это нельзя в интерфейсе.

**Инварианты каждой записи:** результат разбирается обратно (round-trip),
иначе отказ; фронтматтер не может исчезнуть или потерять `saved_at`;
экранирование — через `yaml_quote`.

**Одна граница фронтматтера и сверка (13.10.2026, [SPEC_DEEP_AUDIT.md](SPEC_DEEP_AUDIT.md),
Н1, Е1.1, Е1.2, Е1.6, Е1.9).** Как это устроено сейчас:

- CLI и MCP находят фронтматтер функцией `frontmatter_bounds` из mine-core,
  той же, что у приложения: CRLF, закрывающая строка ровно `---`, файл без
  перевода строки после неё, пустой фронтматтер. `mine card body` печатает
  текст после закрывающей строки, `card set-body` пишет ровно эту часть; у
  файла, который кончается закрывающей строкой, тело начинается с новой
  строки в переводах строк самого файла.
- `card set` и `card unset` пишут поле общим писателем приложения
  (`apply_block_changes`): ключ заменяется или снимается целиком вместе со
  строками продолжения (`|`, `>`, перенос), остальные байты на месте.
  `yaml_quote` экранирует перевод строки и другие управляющие символы
  (`\n`, `\r`, `\uXXXX`) внутри двойных кавычек, поэтому значение с
  переводом строки читается обратно тем же значением. Заметка, чьи свойства
  не читаются как YAML, отказывает.
- Проверка перед записью (`verify_patched`) разбирает результат тем же
  разбором, что приложение (`parse_markdown_document`): фронтматтер не
  исчезает и не перестаёт читаться; каждое свойство, кроме изменённого,
  читается как раньше (`verify_other_properties`, `saved_at` среди них);
  тело то, что задумано. Правка тела оставляет фронтматтер байт в байт.
- Запись публикуется только поверх байтов, которые были прочитаны
  (`write_atomically_if_unchanged`, [SPEC_AUDIT_FIXES.md](SPEC_AUDIT_FIXES.md),
  Ф2): правка снаружи между чтением и записью побеждает, команда отказывает
  кодом 2 словами `<slug> changed outside Mine after it was read; nothing was
  written`.
- Копия для `mine restore` хранит рядом с прежним текстом
  (`cli-backups/<slug>.md`) отпечаток того, что мутация оставила на месте
  карточки (`<slug>.md.left`: SHA-256 байтов или `absent` после удаления).
  `restore` возвращает текст, только пока файл держит именно это: правку,
  сделанную после, и другую заметку, занявшую имя, он не перезаписывает и
  отказывает, называя путь копии. Отказавшая мутация возвращает прежнюю копию
  на место. Копия без отпечатка, сделанная до 13.10.2026, не
  восстанавливается командой, путь к ней назван в отказе.
- После записи заметка индексируется тем же отражением, что у приложения
  (`reconcile::project_source_path`): страница коллекции попадает в
  `channels`, а не в `blocks`. Сбой индекса не глушится: отчёт говорит
  `the index was not updated (<причина>)`, JSON получает поле `index_error`;
  файл записан, приложение доиндексирует его при следующем чтении
  пространства.

**Операции** — переиспользуют доменные операции приложения, без дублирования:

| Группа | Команды |
|---|---|
| Коллекции | создать, переименовать, удалить; `connect`/`disconnect` карточка↔коллекция |
| Карточки | создать (как вставка), переименовать, удалить (тот же план с медиа, что в UI), merge |
| Фронтматтер | `mine card set/unset title\|description\|url\|author\|source <slug>` — только известные поля |
| Тело | `mine card body <slug>` — чтение; `mine card set-body <slug>` (stdin/файл) — замена целиком |

**Защищённые поля:** `Mine Collections` — только через connect/disconnect;
`file` — только профильными медиа-операциями; `saved_at` неизменяем;
произвольные YAML-ключи писать нельзя.

**Присоединение только к странице (решение 10.10.2026).** `mine connect`,
инструмент MCP `connect`, `mine card create --collection` и `card_create` с
`collection` отказывают, если у коллекции нет страницы с `type: channel`:
новый вариант `MutationError::CollectionNotFound { collection }`, код
возврата 4, в stderr `no collection "<имя>": its page does not exist; create
it with mine collection create`, файл карточки не меняется. MCP возвращает
`isError: true` с этим текстом. Страница ищется тем же поиском, что у
`mine collection rename` и `delete`. `disconnect` снимает ссылку и без
страницы. Страницу создают только `mine collection create` и инструмент MCP
`collection_create`. Контракт: [SPEC_COLLECTIONS_OBSIDIAN_LINKS.md](SPEC_COLLECTIONS_OBSIDIAN_LINKS.md),
К5, К7 и К8. Проверку делает `set_collection_membership` в
[cli_mutations.rs](src-tauri/src/cli_mutations.rs) до записи; реализовано
10.10.2026 (PLAN.md, Phase 44).

**Защита тела.** Набор медиа-вставок `![[…]]` до записи обязан совпадать с
набором после; потеря вставки — отказ с перечнем потерянных, сознательное
изменение состава — явный флаг `--allow-media-changes`. Это делает безопасным
основной сценарий «прочитал → перевёл → записал».

**Страховка:** `--dry-run` у каждой мутации (дифф без записи); перед каждой
записью копия прежней версии файла в derived store (не в хранилище — iCloud и
Obsidian её не видят), `mine restore <slug>` возвращает последнюю, пока файл
держит то, что оставила мутация; чтение индекс не трогает. Мутации обновляют индекс: структурные операции
(create/rename/delete/merge, коллекции) пишут его транзакционно тем же кодом,
что и приложение, полевые (set/set-body/connect/disconnect/restore)
переиндексируют карточку после записи файла. Файлы остаются источником истины,
watcher приложения видит те же изменения и сходится к тому же состоянию.

**Решение по объёму:** `delete` и `merge` входят в первую очередь — иначе
«всё то же, что в интерфейсе» не выполняется.

**Статус реализации (27.08.2026).** Реализованы: чтение (5 команд), `card set` /
`unset` известных полей (замена ключа целиком писателем приложения
`apply_block_changes`, `yaml_quote` общий с сериализатором), `card body` /
`set-body` (фронтматтер байт-в-байт, защита вставок), `connect` /
`disconnect` (единственная дверь к `Mine Collections`, через
`patch_collections_frontmatter`), `restore` (своп с копией в derived store,
один уровень в обе стороны, со сверкой с тем, что оставила мутация),
`--dry-run` у всех мутаций. Заметка без фронтматтера отклоняет правку полей: CLI не
изобретает метаданные в чужих файлах.

Структурные операции тоже реализованы и переиспользуют inner-функции
приложения (`rename_block_file_inner`, `delete_block_inner`,
`merge_blocks_inner`, `create/rename/delete_channel_inner`), поэтому
инварианты и транзакционность индекса совпадают с UI один в один:

- `mine card create [--title] [--url] [--collection] [--file] [--from]` —
  карточка без поля `type` (решение 044), слаг по правилам приложения,
  раскладка по `layout.json`;
- `mine card rename <slug> <new-name>`: файл и индекс вместе; страница
  коллекции переименовывается как коллекция (ниже);
- `mine card delete <slug> [--delete-unused-media] [--dry-run]` — тот же план
  медиа, что в UI (dry-run печатает unused/shared); перед удалением текст
  карточки копируется в `cli-backups`, так что `mine restore` возвращает его;
- `mine merge <slug> <slug> […]` — та же композиция, что batch Merge в UI;
- `mine collection create/rename/delete` — страница коллекции и членство в
  карточках обновляются как в приложении, одной операцией на действие
  (13.10.2026, [SPEC_DEEP_AUDIT.md](SPEC_DEEP_AUDIT.md), Н2, Е1.3 по Е1.5;
  [SPEC_COLLECTIONS_OBSIDIAN_LINKS.md](SPEC_COLLECTIONS_OBSIDIAN_LINKS.md),
  К12 по К15):
  - `delete` и инструмент MCP `collection_delete` зовут ту же команду, что
    интерфейс (`delete_channel_inner`): ссылка снимается у каждой карточки и
    страница уходит в Корзину одной мутацией со сверкой. Карточку, которую
    нельзя прочитать или чьи свойства нельзя изменить на месте, удаление
    пропускает и называет: текст `these cards could not be changed and still
    link it: …`, в JSON поле `kept_links`;
  - `rename` сначала сверяет индекс с диском (`reconcile_vault`), затем
    переименовывает страницу, `Mine Collections` участников, ссылки
    `[[Имя]]` в тексте и `Mine Related Notes` так же, как переименование
    карточки;
  - `mine card rename` и инструмент MCP `card_rename` по странице коллекции
    выполняют переименование коллекции; имя с другой папкой отказывает
    (`A collection stays in its folder`);
  - `mine card set`, `unset`, `set-body`, `connect`, `disconnect` и
    `restore` на странице коллекции индексируют её как коллекцию.

Подавление watcher-а (`suppress_paths`) в inner-функциях выполняется только
при наличии `AppState` — из CLI-процесса watcher приложения обязан видеть
внепроцессные изменения.

Удаление файлов идёт тем же путём, что в UI: `delete_user_file` перемещает
`.md` и медиа в системную корзину (безвозвратно — только когда корзина
недоступна, например для некоторых iCloud-заглушек). `cli-backups` — второй
слой поверх корзины: `mine restore` возвращает текст карточки одной командой.

Установка: `bun run cli:install` собирает release-бинарник и кладёт его как
`~/.local/bin/mine`. MCP (этап 2) описан ниже.

## Требования: MCP (этап 2) — реализовано (27.08.2026)

- `mine mcp` — stdio-сервер в том же бинарнике (JSON-RPC 2.0, по строке на
  сообщение): `initialize`, `ping`, `tools/list`, `tools/call`;
- 19 инструментов повторяют подкоманды CLI один в один; адаптер (`mcp.rs`)
  не содержит доменной логики — каждый вызов собирает argv и проходит через
  `cli::run` с `--json`, поэтому охраны, бэкапы и вывод совпадают с CLI по
  построению;
- тела (`card_set_body`, `card_create.body`) передаются строкой аргумента и
  доезжают до CLI через временный файл и `--from`;
- отказ инструмента (карточка не найдена, охрана сработала) возвращается как
  `isError: true` с текстом stderr; повреждённый вызов (нет обязательного
  аргумента, неизвестный инструмент) — ошибка JSON-RPC `-32602`;
- пространство по умолчанию закреплено за процессом сервера (03.10.2026,
  [SPEC_TABS.md](SPEC_TABS.md), В75): первый вызов без параметра `space`
  читает `vault_path` один раз (`CliEnv::default_space`, `OnceLock` в
  `pinned_space`), и до конца процесса все вызовы без `space` получают это
  пространство (`with_pinned_space` в `mcp.rs` подставляет его в аргументы).
  Вызов с явным `space` действует на названное пространство и закреплённое
  не меняет. Без закрепления щелчок по вкладке другого пространства в Mine
  менял бы цель агента между его вызовами, и следующее удаление или слияние
  ушло бы в другое пространство. Описание параметра `space` в схеме
  инструментов говорит об этом: `defaults to the app's current space when
  this server first needed one`. Сменить пространство по умолчанию можно
  перезапуском сервера;
- подключение: `claude mcp add -s user mine -- ~/.local/bin/mine mcp`
  (выполнено 27.08.2026, сервер в user-конфиге) или любой MCP-клиент с
  транспортом stdio; сквозная цепочка «Claude → MCP → mine → хранилище»
  проверена на реальных пространствах.

## Вне объёма

Удалённый доступ и аутентификация, произвольные YAML-ключи, правка файлов вне
известных пространств, «сырые» файловые операции, MCP resources и стриминг.

## Тесты

- интеграционные тесты CLI против фикстурного пространства: каждая
  подкоманда, оба формата вывода, коды возврата, read-only (снимок файлов
  до и после прогона идентичен) — покрыто, включая JSON структурных команд,
  ошибочные пути без побочных эффектов, `--space` для мутаций и восстановление
  удалённой карточки через `restore`;
- поиск без модели эмбеддингов: лексическая деградация с пометкой;
- поиск называет результат именем файла в тексте, в JSON и через MCP, а
  H1 заметки остаётся в `title` (`search_names_a_result_by_its_file_name`
  в `cli.rs` и `mcp.rs`);
- MCP: вызов без `space` получает пространство, закреплённое первым, вызов
  с `space` действует на названное
  (`a_call_without_a_space_keeps_the_space_pinned_first` в `mcp.rs`);
- коллекция только со страницей (решение 10.10.2026, Phase 44): фикстура
  получила страницу `Collections/Nature.md` с `type: channel`, на которую
  ссылается карточка `Cards/sunset`; `connect`, `card create --collection` и
  `cards --collection` по имени без страницы отвечают кодом 4 и ничего не
  пишут; `disconnect` такой ссылки её снимает; `collections` и `card` её не
  показывают; пустая страница в `collections` со счётчиком 0
  (`a_name_without_a_page_is_no_collection_for_the_cli`,
  `an_empty_collection_page_is_listed_with_zero` в `cli.rs`,
  `connect_needs_the_page_and_disconnect_does_not` в `cli_mutations.rs`); MCP
  `connect` и `card_create` к имени без страницы возвращают `isError: true`
  (`connect_to_a_name_without_a_page_is_a_tool_failure` в `mcp.rs`);
- граница фронтматтера, многострочные значения, сверка и коллекции
  (13.10.2026, [SPEC_DEEP_AUDIT.md](SPEC_DEEP_AUDIT.md), Е1.1 по Е1.6,
  Е1.9): настоящие файлы во временном пространстве с CRLF, файлом без
  перевода строки после `---`, пустым фронтматтером, значениями `|` и `>`
  (`source_fidelity_tests` в `cli.rs`;
  `field_and_body_tools_keep_the_note_as_the_app_reads_it` и
  `collection_tools_keep_membership_whole` в `mcp.rs`;
  `a_write_refuses_a_file_changed_after_it_was_read` и
  `a_patch_that_reads_back_differently_is_refused` в `cli_mutations.rs`;
  `a_value_with_line_breaks_reads_back_unchanged` в mine-core);
- параллельный прогон с открытым на запись индексом — покрыт: открытое
  соединение второй стороны и удерживаемая write-транзакция, которую CLI
  пережидает по `busy_timeout`.
