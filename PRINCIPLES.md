# Engineering Principles: Mine

Related documents: [CLAUDE.md](CLAUDE.md) | [ARCHITECTURE.md](ARCHITECTURE.md)

**Этот документ читается перед каждой сессией разработки. Отклонения от принципов требуют явного обоснования и записи в DEVLOG.md.**

---

## Философия

Код — бесплатный ресурс (пишет ИИ). Время — дорогой ресурс (тратит человек на отладку, понимание, переделку). Поэтому мы оптимизируем не скорость написания кода, а его корректность, читаемость и долговечность.

**Мы не делаем MVP.** Мы делаем финальный продукт. Каждый модуль проектируется и реализуется так, как будто его не будут переписывать. Потому что не будут.

---

## Стратегия разработки: вертикальные срезы

Проект реализуется **по модулям**, не по фазам «все спеки → все тесты → весь код». Каждый модуль проходит полный цикл целиком:

```
SPEC (спецификация) → TEST (красные) → CODE (зелёные) → VERIFY → COMMIT
```

### Эталонный модуль

Первый реализованный модуль (`domain/block`) становится **эталоном** — образцом качества, структуры и стиля. Все последующие модули следуют его паттернам. ИИ обучается на конкретном примере в кодовой базе лучше, чем на абстрактных правилах.

### Обучающаяся система

Уроки из реализации модуля N влияют на спецификацию модуля N+1. После каждого модуля — краткая ретроспектива: что узнали, что поправить.

## Принципы

### 1. Контракт первичен

Никакой код не пишется без предварительной спецификации. Порядок:

1. **SPEC** — типы, интерфейсы, поведение, edge cases
2. **Реализация** — строго по спецификации
3. **Тесты** — доказательство соответствия спецификации

Нельзя: «напишу код, потом пойму интерфейс». Нельзя: «тесты добавлю позже».

### 2. Нулевой технический долг

Технический долг — это не компромисс, а дефект. Код либо написан правильно, либо не написан.

**Запрещено:**
- `TODO`, `FIXME`, `HACK`, `TEMP`, `fix later`
- Закомментированный код
- Неиспользуемые импорты, переменные, функции
- `unwrap()` без обоснования в комментарии
- `any` в TypeScript
- `as` касты без объяснения почему это безопасно
- Пустые `catch` блоки
- Магические числа и строки без констант

### 3. Явные границы модулей

Каждый модуль имеет:
- **Публичный интерфейс** — что он экспортирует (типы, функции)
- **Зависимости** — что он импортирует (и почему)
- **Инварианты** — что всегда истинно внутри модуля

`domain/` не знает о `storage/`. `commands/` — тонкий слой, не содержит логики. `storage/` не знает о `commands/`.

### 4. Типобезопасность сквозная

Типы определяются один раз в Rust и автоматически генерируются для TypeScript. Ручное дублирование типов запрещено.

```
Rust (source of truth) → specta/ts-rs → TypeScript (generated)
```

Если тип изменился в Rust, но TypeScript не обновлён — сборка должна упасть.

### 5. Ошибки — граждане первого класса

Каждая ошибка:
- Типизирована (enum, не строка)
- Содержит контекст (что произошло, где, с какими данными)
- Обрабатывается явно (не проглатывается)
- Доходит до пользователя в понятном виде

```rust
// Правильно
#[derive(Debug, thiserror::Error)]
enum IndexError {
    #[error("Failed to parse frontmatter in {path}: {source}")]
    FrontmatterParse { path: PathBuf, source: yaml::Error },
}

// Запрещено
fn index_file(path: &Path) -> Result<(), String> { ... }
```

### 6. Тесты — спецификация в коде

Тесты описывают поведение, не реализацию. Каждый тест отвечает на вопрос «что должно произойти, когда...».

**Обязательно тестируются:**
- Все публичные функции модуля
- Граничные случаи из SPEC
- Некорректные входные данные (что происходит при битом frontmatter, отсутствующем файле, невалидном теге)
- Восстановление после ошибок

**Структура тестов:**
```rust
#[cfg(test)]
mod tests {
    // Arrange — подготовка данных
    // Act — вызов тестируемой функции
    // Assert — проверка результата
}
```

### 7. Документация — часть кода

- `///` doc-comments на всех публичных типах и функциях (Rust)
- JSDoc на всех экспортируемых функциях и компонентах (TypeScript)
- Комментарии объясняют **почему**, не **что**
- README в каждом ключевом модуле, если его назначение неочевидно

### 8. Производительность — архитектурное решение

Производительность закладывается в архитектуру, а не добавляется оптимизациями.

- Виртуальный скроллинг — с первого дня, не «когда станет тормозить»
- Thumbnail-пайплайн — с первого дня, не «пока покажем оригиналы»
- Индексирование — инкрементальное с первого дня, не «пока полное пересканирование»
- Debouncing file watcher — с первого дня, не «потом оптимизируем»

### 9. Конфигурация вместо хардкода

Все параметры, которые могут измениться:

```rust
// Правильно
const THUMBNAIL_SIZE: u32 = 240;
const WATCHER_DEBOUNCE_MS: u64 = 200;
const FTS_SNIPPET_LENGTH: usize = 150;

// Запрещено
image.resize(240, 240); // магическое число в вызове
```

### 10. Идемпотентность операций

Любая операция безопасна при повторном выполнении:
- Пересканирование vault не создаёт дубликатов
- Повторная генерация thumbnail перезаписывает старый
- Повторная индексация файла обновляет, а не дублирует запись
- Пересоздание индекса из файлов даёт тот же результат

## Антипаттерны

Список конкретных практик, которые запрещены в этом проекте:

| Антипаттерн | Почему запрещён | Что делать вместо |
|---|---|---|
| «Потом добавим тесты» | Тесты — часть реализации, не отдельный этап | Писать тесты в той же сессии, что и код |
| «Пока захардкодим» | Хардкод не бывает временным | Вынести в константу или конфигурацию сразу |
| «Упростим для MVP» | MVP-мышление — bias | Сделать правильно с первого раза |
| «Обработаем ошибку позже» | Необработанная ошибка — паника в продакшене | `thiserror` + явная обработка сразу |
| «Скопируем и поправим» | Дублирование — источник рассинхронизации | Выделить абстракцию |
| «Это и так понятно» | Через месяц непонятно никому | Документировать решение и причину |
| Оптимистичный `unwrap()` | Паника вместо ошибки | `?` оператор + контекст через `anyhow`/`thiserror` |
| Строки для ошибок | Нетипизированные, нелокализуемые, неструктурированные | Enum с `#[error]` |

## Чеклист перед коммитом

Каждый коммит проверяется по этому списку:

- [ ] Код соответствует SPEC модуля
- [ ] Все публичные типы и функции документированы
- [ ] Тесты написаны и проходят
- [ ] Нет `TODO`, `FIXME`, `HACK`, закомментированного кода
- [ ] Нет `unwrap()` без обоснования
- [ ] Нет `any` в TypeScript
- [ ] Ошибки типизированы и содержат контекст
- [ ] Магические числа вынесены в константы
- [ ] `cargo clippy` без предупреждений
- [ ] `bun run lint` без ошибок
- [ ] ARCHITECTURE.md актуален (если менялась структура)
- [ ] PLAN.md актуален (если менялся статус задач)
