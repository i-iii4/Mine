# SC0: проверка сохранения и повтора

Дата: 31.08.2026. База проверки: `d4f4c8c` и добавленные SC0-тесты.
Контракт: [SPEC_SAVE_CORE.md](../SPEC_SAVE_CORE.md).
План: [SC0–SC7](../PLAN.md#save-core-plan).

Этот отчёт сохраняет **историческую диагностику до переноса**. Нативные N2–N5
затем исправлены; текущие тесты проверяют безопасный результат, а не баги.
Актуальный код и результаты — [итог переноса](save-core-acceptance.md).
B1–B3 на настоящей системной папке остаются непроверенными; автоматизация
диалога исключена из предусловий разработки по указанию пользователя.

## Проверенный результат

Пять диагностических тестов проходят, **в том числе когда воспроизводят
дефект**. Это не пять исправлений. При исправлении соответствующего пути
ожидания N2–N5 должны проверять безопасный результат, а не сохранять дефект
ради зелёного теста.

| Проба | Фактический результат | Вывод |
|---|---|---|
| N1: два `write_new_atomically` | Один полный файл; проигравший получает `AlreadyExists`; следующая запись не меняет байты; временных файлов не осталось | Примитив отказывает при занятом имени; это не гарантия всего host |
| N2: два `finalize_pending_upload` с тем же ID | Созданы `Door.jpg` и `Door (2).jpg`; manifest не изменился | Нет подтверждения первого результата; повтор финализации не идемпотентен |
| N3: отброшен ответ успешного host, повторён ID | Карточка существует; staging удалён; тот же ID возвращает `failed to read pending upload`; новый upload ID создаёт вторую карточку | Потеря ответа не обрабатывается как проверка предыдущего commit |
| N4: реконструирован диск после Markdown до cleanup | Повтор того же ID создаёт вторые Markdown и медиа, первые остаются | Оставшийся staging не позволяет распознать состоявшийся commit |
| N5: legacy upload при занятом `Media/Door.jpg` | Существующие байты заменены новым upload | Проверка имени смотрит в корень, rename пишет в настроенную папку медиа; дефект есть без гонки |
| B1: видимость файла до browser close | Не выполнена | Нужен настоящий OS-directory handle |
| B2: внешний create между lookup и browser write | Не выполнена | Отсутствие no-clobber ожидается по API, но runtime-результат ещё не получен |
| B3: exclusive writer против browser/Node | Не выполнена | Внутрибраузерный lock нельзя объявлять общесистемным |

N3 отбрасывает сериализованный ответ в тесте; реальная ошибка pipe не
инжектируется. N4 — реконструкция файлового состояния, не убийство процесса.
N1 не проверяет отключение питания или наблюдение файла на каждом системном
вызове. Все записи тестов — в новых `tempfile`-каталогах.

Отдельное незакрытое окно найдено чтением кода: после успешного `hard_link`
ошибка `sync_parent_directory` возвращается как обычный `Err`. Host может
запустить cleanup медиа, хотя Markdown уже опубликован. **Этот отказ fsync
не воспроизводился**; нужна управляемая точка отказа и проверка полного пути.

## Воспроизведение native

Запускать из корня репозитория. Проверенная среда: Rust/Cargo 1.95.0,
macOS 27.0. Команды не открывают пользовательский vault.

```sh
cargo test -p mine --lib --bin native-host --locked sc0_ -- --nocapture
cargo test -p mine --bin native-host --locked
cargo test -p mine --lib --locked storage::files::tests
cargo test -p mine --lib --locked storage::clipper_uploads::tests
```

Результаты: SC0 **5/5**, весь native-host **68/68**, `files` **13/13**,
`clipper_uploads` **7/7**. Группы пересекаются; складывать их как число
уникальных тестов нельзя. Два прежних предупреждения — `NSFilenamesPboardType`.

Отдельная существующая проблема: сборка с `--no-default-features` падает
на обращениях к `commands`/`tauri` без соответствующего feature gate.
Это важно для SC1: текущий app-crate нельзя объявлять уже переносимым ядром.
Cargo-файлы и feature-gating в этой работе не менялись.

После перемещения checkout старые Swift/Tauri build caches ссылались на
прежний путь. Swift cache сохранён отдельно во временной папке; только
генерируемые артефакты пакета Tauri пересозданы. Обычная сборка после этого
проходит. Очистка всего рабочего дерева не выполнялась.

## Воспроизведение browser

Ручной стенд проб B1, B2 и B3 (`scripts/sc0-fsa-probe.mjs` и `scripts/sc0-fsa-probe.html`)
удалён 13.10.2026 по находке Е7.10 ([SPEC_DEEP_AUDIT.md](../SPEC_DEEP_AUDIT.md)).
Ему нужна настоящая системная папка: `showDirectoryPicker({mode:'readwrite'})`
открывается только по жесту пользователя в системном окне выбора, которое
Playwright заполнить не может. Без окна такой стенд не становится
автоматической проверкой, а ручной прогон исключён из предусловий разработки
по указанию пользователя. OPFS, поддельная файловая система и Playwright
`setInputFiles` системную папку не заменяют. Результаты характеристики выше
остаются как есть: B1, B2 и B3 не выполнены.

## Инвентарь для переноса

| Клиент | Текущий владелец создания/записи | Граница, которую нельзя потерять |
|---|---|---|
| Host | `native_host::handle_save_block`; общий Rust serializer, собственный сборщик | Новая карточка не должна зависеть от доступности индекса; сейчас DB всё ещё открывается до записи |
| Desktop | `commands::blocks::create_block` → `persist_new_block` | `StagedSourceMutation` содержит runtime rollback с SQLite; это не долговечный журнал аварий |
| CLI create/структурные изменения | Свой сборщик + desktop/storage helpers | Известный vault, текущие guards, dry-run и rollback |
| CLI поля/body/membership | Текстовые patchers + backup + atomic replace | Чужие frontmatter-поля и существующие media refs; последующий best-effort reindex |
| MCP | Tools → CLI argv → `cli::run` | API уже содержит мутации; только читающие вызовы остаются без записи |
| iOS core-ffi | Parse/list/scan/speech | Экспортированного save API сейчас нет; не добавлять мобильные функции под видом переноса |
| Standalone | Независимые JS serializer/names/layout/save | Нет журнала или глобальной очереди; формат `type/title` расходится с новым native |

## Что остаётся до закрытия SC0

- Выполнить B1–B3 с реальной папкой и занести байты/ошибки в таблицу.
- Закрыть файловый контракт browser. Если нужны новые имена, папка приёма,
  обязательный helper или более слабая сохранность — получить отдельное
  продуктовое решение, не подменять его общей архитектурой.
- Проверить аварийные границы, включая fsync после публикации, journal loss
  и повтор после перезапуска, а не только реконструкцию состояния.
- Зафиксировать окончательный контракт журнала, его размещение, переход
  старого staging и защиту от одновременного старого host/cleanup.
- Только после этого начинать SC1. Подготовленные типы в спецификации пока
  не означают закрытый файловый контракт.
